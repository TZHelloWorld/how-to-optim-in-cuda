## 8.1 APOD 优化方法论

清单可以列一百条，但没有方法论的清单只会让人无从下手。所以在翻开任何一张优化清单之前，先回答三个更根本的问题：优化应该按什么流程推进？一堆可做的优化里先做哪个？做到什么程度算"够了"？这一节依次给出官方 Best Practices Guide 的三个答案：APOD 循环、优先级原则和扩展性/Roofline 分析。

### 8.1.1 四步一循环：Assess、Parallelize、Optimize、Deploy

NVIDIA Best Practices Guide 推荐的迭代式优化流程 **APOD**：

```text
        ┌──────────────────────────────────────────────┐
        │                                              ▼
   Assess（评估） → Parallelize（并行化） → Optimize（优化） → Deploy（部署）
   分析热点，找出          用库/OpenACC/CUDA       按瓶颈逐项优化，        尽早上线验证，
   最值得并行的部分        实现并行版本            小步快跑              再进入下一轮
```

逐步展开：

1. **Assess（评估）**：用 profiler 找出程序中**耗时占大头的热点函数**——很多程序的绝大部分时间花在很小一段代码上。结合 Amdahl 定律（见第 1 章 1.3.3 节）估算"把这部分并行化，整体最多能快多少"，先设定合理预期再动手；
2. **Parallelize（并行化）**：实现并行版本。注意官方给出的顺序是**能用库就用库**（cuBLAS、cuFFT、Thrust 等，见第 1 章 1.4.3 节），其次是 OpenACC 等指令式编译器，最后才是手写 CUDA C++ 内核——手写灵活性最高，但成本也最高；
3. **Optimize（优化）**：并行版本跑通后，按瓶颈逐项优化。这本身也是一个小循环："发现优化点 → 应用 → 实测验证 → 重复"，不必一开始就背下所有优化技巧，**边学边用、增量应用**即可（8.3~8.6 节的清单就是为这一步准备的）；
4. **Deploy（部署）**：完成一轮加速后**尽早部署到生产环境**，哪怕加速是部分的——让投入尽早产生价值，也让改动以渐进而非革命的方式落地、降低风险。然后带着真实反馈回到 Assess，开始下一轮循环。

> [!IMPORTANT]
> APOD 的精髓是"**循环**"二字：不追求一步到位的完美优化，而是每一圈都产出一个更快且可用的版本。新人最常见的反面做法是闷头优化三个星期不验证——方向一旦错了，三个星期全部作废。

配套的两条纪律：

1. **先正确，再快**：每一步优化都要有正确性验证（对照 CPU 结果）；
2. **用数据说话**：每一步优化都要有 profiler 佐证（改前改后对比），不猜测瓶颈。

> [!NOTE]
> 关于"先正确"再补充两点官方提醒：① 浮点运算**不满足结合律**，并行化会改变运算顺序，GPU 结果和 CPU 结果常有微小差异——验证时应使用容差（epsilon）比较而不是逐位比较；② 验证正确性的对照流程可以顺手扩展成验证性能的流程，让"每次改动既没改错、又确实变快了多少"成为 APOD 循环的固定动作。

### 8.1.2 优化的优先级：先"喂饱"GPU，再抠细节

Optimize 这一步可做的事很多，官方文档专门把所有建议**按优先级分类**（效果大、适用面广的优先级最高），并强调：**做低优先级优化之前，先确认所有相关的高优先级建议已经做完**——这能让时间投入获得最好的回报，也能避免"过早优化"的陷阱。按这个原则，本书涉及的优化大致排出如下先后：

1. **第一优先级：暴露足够的并行度**。GPU 靠海量线程轮转隐藏延迟（见第 4 章 4.4 节），线程不够一切免谈——首先保证启动了成千上万的线程、有足够多的常驻 warp；
2. **第二优先级：访存效率**。绝大多数内核是访存受限的，重点依次是：**减少主机-设备传输**（见第 6 章）、**全局内存合并访问**（见第 5 章 5.2 节）、**用好共享内存并避免 bank 冲突**（见第 5 章 5.3 节）；
3. **第三优先级：指令级细节**。前两项做好之后，才轮到避免 warp 分化（见第 4 章 4.5 节）、循环展开（见第 4 章 4.7 节）、用 shuffle 替代共享内存（见第 7 章）、快速数学函数、减少原子操作竞争等微调。

一句话记忆：**先让几千个"工人"都有活干、原材料供得上，再去打磨每个工人的动作细节。** 顺序反了，就是在给一台大部分时间在空转的机器抛光。

### 8.1.3 加速上限：强扩展与弱扩展

Assess 阶段要估算加速上限，官方文档给出两把尺子，分别对应两类问题：

- **强扩展（Strong Scaling）**：**问题总规模固定**，增加处理器数量能把求解时间缩短多少。它由 **Amdahl 定律**刻画（第 1 章 1.3.3 节已详细推导）：设可并行部分占比为 $P$、处理器数为 $N$，则加速比 $S = \dfrac{1}{(1-P) + P/N}$；$N$ 很大时上限为 $\dfrac{1}{1-P}$——串行部分决定天花板，所以**最值得花力气的是提高 $P$，即把更多代码并行化**；
- **弱扩展（Weak Scaling）**：**每个处理器分到的问题规模固定**，总问题规模随处理器数量同步增长（保持求解时间不变，做更大的问题）。它由 **Gustafson 定律**刻画：$S = N + (1-P)(1-N)$——只要问题能随硬件"长大"，加速几乎不封顶。

两把尺子怎么选？看你的问题规模会不会增长：模拟两个固定大小的分子如何相互作用，问题规模不变，适用强扩展；流体网格模拟、蒙特卡洛模拟这类"网格可以加密、样本可以加多、精度随之提高"的问题，适用弱扩展。**理解自己的应用属于哪一类，是设定合理加速预期的前提**——很多"GPU 加速 100 倍"的宣传，其实说的是弱扩展场景。

### 8.1.4 Roofline 思维：访存受限还是计算受限

知道了上限，还要知道单个内核该往哪个方向优化。判断内核的理论上限用 **Roofline 思维**——先算内核的**算术强度**（Arithmetic Intensity，每从内存搬运 1 字节数据平均做多少次浮点运算，单位 FLOPs/Byte），再对照硬件的算力/带宽比：

- 算术强度（FLOPs/Byte）低的内核（向量加法、转置、归约）是**访存受限**——目标是逼近显存带宽，优化重点在第 5 章；
- 算术强度高的内核（GEMM、卷积）是**计算受限**——目标是逼近 FLOPS 峰值，优化重点在指令吞吐与 Tensor Core。

举个数：向量加法每读写 12 字节只做 1 次加法，算术强度约 0.08 FLOPs/Byte，而现代 GPU 的"算力 ÷ 带宽"普遍在几十 FLOPs/Byte 以上——所以向量加法无论怎么优化计算都没用，**它的性能上限就是显存带宽**，衡量它的正确标尺是 8.2.2 节的有效带宽。**搞错内核的受限类型，后面的所有优化都会用错力气**，这也是 Nsight Compute 报告里 Roofline 图表被放在显要位置的原因（见 8.8 节）。

## 8.2 性能度量：先学会正确地测

方法论说"用数据说话"，那数据本身必须可信——**测错了的性能数据比没有数据更危险**，它会把优化引向完全错误的方向。这一节讲两件事：怎么正确计时，以及用什么指标衡量优化效果。

### 8.2.1 计时：预热、同步与 CUDA Event

CUDA 计时有三个新人几乎必踩的坑，逐一说明：

1. **内核启动是异步的，不同步就停表等于没测**。第 1 章就强调过：`<<<...>>>` 发出后 CPU 立即继续执行，带 `Async` 后缀的拷贝函数同理。用 CPU 计时器（如 `std::chrono`）测内核耗时，必须在**启动计时前和停止计时前各调用一次** `cudaDeviceSynchronize()`，否则测到的只是"发命令"的时间（典型症状：内核"耗时"约 0 毫秒，见 8.7 节陷阱表）；
2. **计时前要预热（warm-up）**。程序中第一次 CUDA 调用会触发上下文初始化，第一次内核启动还可能包含 JIT 编译（见第 1 章 1.8.3 节）等一次性开销——正式计时前先把待测内核空跑一两遍，然后**多次运行取平均**，结果才稳定可比；
3. **首选 CUDA Event 计时**。第 3 章 3.9 节已经给出完整用法：`cudaEventRecord` 把事件插入流中，GPU 到达该点时记录时间戳，`cudaEventElapsedTime` 返回毫秒差值。官方指出其分辨率约为**半微秒**，且**基于 GPU 时钟**，结果与操作系统无关——比 CPU 计时器更精确，也不需要阻塞整个设备。

> [!WARNING]
> `cudaDeviceSynchronize()` 这类主机-设备同步点会让 GPU 流水线停顿，本身就有性能代价——它是计时工具，不要留在生产代码的热路径里（第 6 章"减少全局同步"讲的正是这个）。另外，若程序使用了多个非默认流，事件计时可能把其他流中交错执行的工作也算进来——测单内核时用默认流最稳妥。

### 8.2.2 带宽：用有效带宽衡量优化效果

计时告诉你"跑了多久"，但"3 毫秒"本身不说明快慢——还差一个参照系。对访存受限的内核（多数内核如此），官方给出的**高优先级建议**是：**用有效带宽（effective bandwidth）作为度量优化效果的指标**，并与理论带宽对比判断还有多少余量。

**理论带宽**由硬件规格算出。以 NVIDIA Tesla V100 为例：HBM2 显存时钟 877 MHz、位宽 4096 bit、双倍数据率（DDR），则峰值理论带宽为

$$(0.877 \times 10^{9}) \times (4096 / 8) \times 2 \div 10^{9} = 898\ \text{GB/s}$$

**有效带宽**由程序实测算出：统计内核实际读、写的字节数，除以耗时：

$$\text{有效带宽} = \frac{(B_r + B_w) \div 10^{9}}{\text{time}}$$

其中 $B_r$、$B_w$ 分别是内核读取和写入的字节数，time 单位为秒。例如拷贝一个 2048×2048 的 float 矩阵，读写各一遍：$(2048^2 \times 4 \times 2) \div 10^9 \div \text{time}$。若实测有效带宽只有理论带宽的两三成，说明访存模式有问题（不合并、跨步、非对齐——对照 8.3 节清单逐项排查）；若已达八九成，这个内核基本"到顶"了，再优化也榨不出多少。

> [!NOTE]
> 两个容易忽略的细节：① 分母用 $10^9$（GB）还是 $1024^3$（GiB）都可以，但**理论带宽和有效带宽必须用同一个除数**，否则对比无效；② 开启 ECC 的 GDDR 显存会损失约 6.25% 容量、有效带宽还会再降约 20%（HBM2 有独立的 ECC 资源，无此开销）——对比不同机器的数据时要留意。

方法和尺子都有了，接下来四节是可以逐项对照的优化清单——它们分别浓缩自第 5、4、5、6 章，建议在优化真实内核时挨行打钩。

## 8.3 全局内存访问优化清单

四张清单从最重要的开始：全局内存是几乎所有内核都要走的"主干道"，也是第一优先级之后最常见的瓶颈所在。基于第 5 章 5.2 节的分析（warp 视角的访问、内存段与事务、缓存行为、访问模式图解），提高全局内存访问效率的关键原则汇总如下：

| 原则 | 说明 | 文档依据 |
|------|------|---------|
| **使用 `cudaMalloc` 分配内存** | 自动保证 ≥256 字节对齐，所有基本类型天然对齐 | Programming Guide §8.3.2 |
| **线程块大小为 warp 大小的倍数** | 保证每个 warp 的访问地址在同一对齐块内 | Best Practices Guide §10.2.1.2 |
| **连续线程访问连续地址（stride=1）** | 4 个 32 字节事务，100% 带宽利用率 | Best Practices Guide §10.2.1.1 |
| **避免跨步访问** | stride=2 → 50% 效率；用 Shared Memory 中转 | Best Practices Guide §10.2.1.4 |
| **数据布局优先 SoA 而非 AoS** | warp 访问同一成员时地址连续、可合并 | 见 5.2.4 节 |
| **结构体使用 `__align__(8/16)`** | 防止多指令访问，保证自然对齐 | Programming Guide §8.3.2 |
| **2D 数组使用 `cudaMallocPitch`** | 自动 padding，保证每行地址对齐 | Programming Guide §8.3.2 |
| **频繁重用数据用 L2 持久化（CC 8.0+）** | `cudaAccessPropertyPersisting`，减少 DRAM 访问 | Programming Guide §6.2.3 |
| **只读数据使用 `__ldg()` 或 `const __restrict__`** | 走 L1 read-only cache，带宽更高 | Programming Guide §20.4.2 |
| **向量化加载（float4 等）** | 单指令搬 16 字节，减少指令数（注意对齐要求） | 见 5.2.2 节 |

这张表的前四行合起来就是一句话：**让同一 warp 的 32 个线程访问同一段对齐且连续的地址**——第 5 章反复推演的"合并访问"是全局内存优化的第一性原理，其余各行都是它在不同场景下的具体化。验证做没做到位，用 8.8 节的 `ncu` 看访存效率指标即可。

## 8.4 执行配置与计算优化清单

访存喂得上了，还要保证"工人"排班合理——执行配置决定了 SM 上有多少活跃 warp 可供调度器轮转（第 4 章的核心主题），计算方式决定了每个 warp 的指令效率。相关原则汇总：

| 原则 | 说明 |
|------|------|
| **块内线程数取 32 的倍数（推荐 128~512）** | 避免残缺 warp，warp lane 资源最大化 |
| **保证足够多的常驻 warp（占用率）** | 依靠零开销 warp 切换隐藏访存延迟 |
| **避免 warp 内分支分化** | 让条件分支的粒度对齐 warp；归约等算法用连续线程干活 |
| **手工/`#pragma unroll` 展开核函数内循环** | CUDA 编译器不会自动充分展开，人为展开常有显著收益 |
| **控制寄存器与共享内存用量** | 资源超额会降低 SM 常驻块数，减少活跃 warp |
| **块间不要有数据依赖** | CUDA 只提供块内同步；块间协作需拆分内核或用原子操作 |
| **每线程多干活（grid-stride loop）** | 摊薄索引计算与调度开销，提高指令级并行 |

逐行溯源：块大小与 warp 的关系见第 4 章 4.3 节，占用率与延迟隐藏见 4.4 节，分化与归约实例见 4.5、4.6 节，循环展开见 4.7 节；grid-stride loop 见第 2 章 2.5 节；块大小的选择方法见第 2 章 2.6 节。有两点提醒：

> [!TIP]
> 占用率不是越高越好——它只需要**高到足以隐藏延迟**。有时每线程多用一些寄存器换取更少的全局内存访问，虽然占用率下降，总性能反而更好。结论仍然是那句话：**改完用 profiler 实测，不猜测**。

> [!NOTE]
> 计算侧还有一条 8.7 节陷阱表会再次出现的规则：**消费级 GPU 的 FP64 吞吐只有 FP32 的几十分之一**——精度够用时用 `float`，并把字面量写成 `1.0f`（否则 `1.0` 是 double，会把整个表达式提升为双精度运算）。

## 8.5 共享内存优化清单

执行配置排好班后，下一层是块内协作的主战场——共享内存。它是把"糟糕的全局内存访问模式"转化为"良好模式"的中转站（第 5 章 5.3 节），但用不好自己也会成为瓶颈（bank 冲突）。关键原则：

| 原则 | 说明 |
|------|------|
| **交错/转置访问先经共享内存中转** | 把全局内存的交叉访问转化为合并访问 |
| **避免 bank 冲突：步长取奇数** | `gcd(32, s) = 1` 时无冲突 |
| **二维 tile 使用 +1 padding** | `tile[32][33]` 使按列访问从 32 路冲突降为无冲突 |
| **注意宽类型（double/float4）的 bank 行为** | 宽类型横跨多个 bank，需按实际触碰的 word 分析 |
| **`__syncthreads()` 保护读写顺序** | 共享内存装载与消费之间必须块内同步 |
| **warp 内部通信优先用 shuffle** | 比共享内存延迟更低，且不占共享内存容量 |

前四行的原理与实例（矩阵转置、归约）见第 5 章 5.3 节；第五行"装载-同步-消费"的配对是共享内存正确性的生命线，漏掉会产生与块大小相关的偶发错误（见 8.7 节陷阱表）；最后一行的 shuffle 指令见第 7 章 7.4 节——**当通信范围不超过一个 warp 时，shuffle 几乎总是比共享内存更好的选择**。

## 8.6 主机-设备交互优化清单

内核本身优化到位之后，把视野拉回整个应用——很多程序的瓶颈根本不在 GPU 上，而在 CPU 与 GPU 之间那条"窄公路"上（第 1 章 1.3.1 节：PCIe 带宽比显存带宽低 1~2 个数量级）。第 6 章的结论汇总：

| 原则 | 说明 |
|------|------|
| **能不传就不传** | 数据尽量常驻 GPU，中间结果不回传 |
| **合并小传输为大传输** | 每次 `cudaMemcpy` 都有固定启动开销 |
| **频繁传输的缓冲区用锁页内存** | `cudaMallocHost`，带宽约 2 倍，且支持异步 |
| **多流流水线重叠传输与计算** | 见第 6 章，可获得最高 2~3 倍吞吐 |
| **减少全局同步** | 用流/事件粒度同步替代 `cudaDeviceSynchronize` |

第一行值得再强调一遍，因为它是官方的**最高优先级建议之一**：即使某个中间步骤在 CPU 上算得更快，只要把它留在 GPU 上能省掉一来一回的传输，**用一个相对慢的内核换掉传输往往也是赚的**。判断一段计算值不值得搬上 GPU，要看"每传输一个数据元素能做多少次运算"——矩阵加法是 $O(1)$（传 $3N^2$ 个元素只做 $N^2$ 次加法），单独做不划算；矩阵乘法是 $O(N)$，矩阵越大越划算。锁页内存的原理见第 5 章 5.1.7 节，多流重叠的完整做法见第 6 章 6.3 节。

## 8.7 新人常见错误与陷阱

清单管"怎么做对"，这一节管"错在哪里"——以下是新人最常撞上的症状，按"症状 → 原因 → 排查"组织，调试时可当急诊手册查：

| 症状 | 常见原因 | 排查方法 |
|------|---------|---------|
| 结果全是 0 / 没变化 | 忘了 `cudaMemcpy` 回传；内核启动失败被忽略 | 每次启动后 `CHECK(cudaGetLastError())`（见第 3 章 3.8 节） |
| 结果随机错误 | 缺少边界检查越界写；竞争条件缺原子操作（见第 7 章） | `compute-sanitizer ./app` |
| 死锁 / 卡住 | `__syncthreads()` 放在分支里，部分线程到不了 | 检查所有条件分支内的同步 |
| 偶发错误、与块大小相关 | 共享内存读写间缺 `__syncthreads()` | 审查共享内存的生产-消费配对 |
| 计时结果 ~0 ms | 内核异步启动，没同步就停表 | 用 cudaEvent 计时（3.9 节） |
| "unspecified launch failure" | 非法内存访问（GPU 版段错误） | `compute-sanitizer`，检查指针是否设备指针 |
| 用主机指针传给内核 | `malloc` 的指针不能在内核里解引用 | 区分 h_/d_ 前缀命名习惯 |
| 性能远低于预期 | 访存不合并 / 分化 / 占用率低（见第 4、5 章） | `ncu` 看 gld_efficiency、分化、occupancy |
| double 运算奇慢 | 消费级 GPU 的 FP64 单元只有 FP32 的 1/32~1/64 | 能用 float 就用 float，字面量写 `1.0f` |
| Debug 构建（`-G`）性能极差 | `-G` 关闭所有设备代码优化 | 性能测试务必用 `-O3` 且不带 `-G` |
| 原子操作成为热点 | 大量线程 `atomicAdd` 同一地址，硬件被迫串行化 | 先做块内/warp 内归约再原子累加（见第 7 章 7.3 节） |
| GPU 大部分时间在空闲 | 循环里反复做小规模 H2D/D2H 传输，传输次数多、每次量小 | `nsys` 看时间线；合并传输、数据常驻 GPU（见第 6 章） |
| 块大小非 32 的倍数 | 结果正确但残缺 warp 浪费算力 | 块大小取 32 的倍数（见第 1 章 1.5.5 节、第 2 章 2.6 节） |

> [!TIP]
> 这张表里出镜率最高的两个工具是 `CHECK` 宏（第 3 章 3.8 节）和 `compute-sanitizer`。养成两个习惯能避开表中一半的坑：**每个 CUDA API 调用都检查返回值、每次内核启动后都查 `cudaGetLastError()`**——官方文档特意注明，指南里的示例代码为了简洁省略了错误检查，但**生产代码必须逐调用检查**。

## 8.8 性能分析工具速查

前面的清单和陷阱表都反复出现同一句话："用 profiler 看"。最后把工具本身讲清楚——用哪个、什么时候用、看什么指标。优化的完整闭环：**先保证正确性 → 用 profiler 定位瓶颈（带宽 / 计算 / 延迟）→ 针对性优化 → 实测验证**。

### 8.8.1 Nsight Systems 与 Nsight Compute 的分工

现代 NVIDIA 工具链的两大件各司其职，**先宏观后微观**是标准用法：

- **Nsight Systems（`nsys`）——先用它看全局**：生成整个应用的时间线（CPU 活动、CUDA API 调用、内存传输、各内核耗时）。它回答的是宏观问题：时间花在传输还是计算？GPU 是否长时间空闲等 CPU？多流有没有真正重叠？哪个内核最耗时、最值得优化？——对应 APOD 的 Assess 阶段；
- **Nsight Compute（`ncu`）——再用它看单个内核**：对选定内核做深度剖析（SM 利用率、访存效率、占用率、Roofline 图、warp 停顿原因）。它回答的是微观问题：这个内核是访存受限还是计算受限？合并访问做到位了吗？瓶颈具体卡在哪条流水线上？——对应 Optimize 阶段的靶向诊断；
- **compute-sanitizer——正确性守门员**：检测非法内存访问、竞争条件、同步错误，属于"先正确再快"的第一道关卡。

一句话分工：**`nsys` 找到"哪个内核有问题"，`ncu` 找到"这个内核的问题在哪"，`compute-sanitizer` 保证你优化的是一个正确的程序。**

### 8.8.2 常用命令与经典指标

```bash
# 现代工具链
nsys profile ./app                       # Nsight Systems：时间线、API 调用、核函数耗时
ncu --set full ./app                     # Nsight Compute：单核函数深度分析（利用率、访存效率、占用率）
compute-sanitizer ./app                  # 内存错误 / 竞争检测

# 经典指标（老工具 nvprof）
nvprof --metrics gld_efficiency,gst_efficiency ./app   # 全局加载/存储效率
nvprof --metrics inst_per_warp ./app                   # warp 平均指令数（衡量分化）
nvprof --metrics shared_load_transactions_per_request ./app  # 共享内存 bank 冲突程度
```

> [!NOTE]
> `nvprof` 在新架构（Volta 之后）上已被 `nsys`/`ncu` 取代，但它的指标名（如 `gld_efficiency`）在大量教程和历史资料中仍随处可见，知道对应关系有助于读懂旧资料——在 `ncu` 中可用 `ncu --query-metrics` 查询新指标体系里的对应项。

## 8.9 综合实战练习：把全书串起来

工具在手、清单在册，最后用一个项目检验全部所学。以下是一个循序渐进的毕业项目，覆盖全书所有知识点——**实现并逐级优化一个完整的 softmax 内核**（输入 `[rows, cols]` 矩阵，对每行做 softmax）：

1. **v0 正确性基线**：每行一个线程，先写对（第 1~3 章：内存管理、索引、错误检查）；
2. **v1 每行一个 block**：块内线程并行处理一行，用共享内存 + 块内归约求行最大值与行和（第 4 章、第 5 章 5.3 节）；
3. **v2 消除分化 + warp shuffle**：归约部分改用 warp shuffle 三层归约（第 7 章）；
4. **v3 访存合并检查**：确认相邻线程读相邻列，用 `ncu` 验证 `gld_efficiency` 接近 100%（第 5 章 5.2 节）；
5. **v4 向量化加载**：`float4` 一次读 4 个元素（第 5 章 5.2 节）；
6. **v5 多流批处理**：多个矩阵用多流重叠传输与计算（第 6 章）；
7. **收尾**：每个版本记录耗时与带宽，画出优化演进曲线，写一份优化报告（APOD 方法论，本章）。

做这个项目时，请刻意练习本章的方法论：每个版本先用 8.2 节的方法**正确计时并计算有效带宽**，对照 8.1.4 节判断当前受限类型，再从 8.3~8.6 节的清单里挑下一个优化点——让"度量 → 诊断 → 优化 → 验证"的循环成为肌肉记忆。完成后可以对照 PyTorch 的 `torch.softmax` 实测性能，你会对"手写内核 vs 工业级实现"的差距有直观认识。

## 8.10 本章小结

把本章（也是全书的优化知识）收拢成几句话：

- **方法论**：优化按 APOD 循环推进（评估 → 并行化 → 优化 → 部署，小步快跑、尽早上线）；两条纪律——先正确再快、用数据说话；
- **优先级**：先暴露足够并行度（第 4 章），再抓访存效率（第 5、6 章），最后抠指令级细节（第 4、7 章）——高优先级没做完之前不碰低优先级；
- **加速上限**：固定问题规模看强扩展（Amdahl 定律，第 1 章），问题随硬件增长看弱扩展（Gustafson 定律）；单内核用 Roofline 思维判断访存受限还是计算受限，再决定优化方向；
- **度量**：计时要预热、要同步，首选 CUDA Event（第 3 章）；访存受限内核用**有效带宽**对照理论带宽衡量优化空间；
- **四张清单**：全局内存的核心是**合并访问**（8.3），执行配置的核心是**足够的活跃 warp**（8.4），共享内存的核心是**中转 + 防 bank 冲突 + 同步配对**（8.5），主机-设备交互的核心是**能不传就不传、传就重叠**（8.6）；
- **排障**：常见错误对照 8.7 节的表；`CHECK` 宏 + `compute-sanitizer` 守正确性，`nsys` 看宏观、`ncu` 看微观。

## 8.11 进阶学习路线与全书结语

本书的内容到此全部结束，但 CUDA 的学习远未到头——前 8 章给你的是一张完整的"地基图纸"，真正的功力要在持续的实战中长出来。完成本指南后，可以沿以下方向继续深入：

1. **经典内核手写练习**：GEMM（矩阵乘）逐级优化（tiling → 双缓冲 → Tensor Core）、softmax、layernorm、scan（前缀和）——这是面试与实战的硬通货；
2. **官方库源码**：CUB（块级/设备级原语库）、Thrust（并行 STL）、CUTLASS（GEMM 模板库）——读它们的源码，就是在看第 4、5、7 章的知识点被工业级地运用；
3. **高级特性**：CUDA Graph（降低启动开销）、异步拷贝 `cp.async`（Ampere+）、TMA（Hopper）、动态并行、多 GPU（NCCL）——其中 CUDA Graph 在第 6 章的深度专题中已有入门介绍；
4. **PTX/SASS 层面**：`nvcc -ptx` 与 `cuobjdump --dump-sass` 查看编译产物，理解编译器行为（编译流程的基础见第 1 章 1.8 节）；
5. **持续阅读**：每代新架构的 Tuning Guide、GTC 技术演讲、[CUDA C++ Programming Guide](https://docs.nvidia.com/cuda/cuda-c-programming-guide/index.html) 的更新章节。

回望全书：第 1 章我们从"为什么需要并行"出发，一路把线程层次、执行模型、内存层次、流与并发、原子与 warp 原语收入囊中，最终在本章汇成一套可操作的方法论。如果只带走一样东西，请带走这个循环——**度量、诊断、优化、验证**：它比任何具体技巧都更长久，因为架构会换代、指标会更名，而这套思维方式不会过时。

> 想写出更快更好的 CUDA 程序：**学习硬件执行模型，学习使用测试工具，多思考、多总结、多练习。**

祝你写出又快又对的内核。
